Project Overview

Research date: 24 October 2026 | Revision: 445eb11

Recommendation

Recompose the existing system into one installable Python application around its deterministic financial semantics and one execution owner.

Key Features

Tiered Architecture

Three-tier system with Tier-1 for financial authority, Tier-2 for cognition, and clear separation of concerns.

Agentic Cognitive Fabric

Bounded AI coordination with role-scoped capabilities, memory partitioning, and evidence-based decision making.

Deterministic Canvas

Reproducible market intelligence scratchpad for agentic use with causal fact tracking.

Evidence-Driven

Immutable evidence bundles, hash-chained ledgers, and comprehensive audit trails.

Target Architecture

Architecture Principles

  • One canonical financial history and one execution owner
  • Governed, evidence-driven agentic trading platform
  • Production and simulation share code but not authority
  • Deterministic Market Canvas with full scratchpad capability
  • Bounded AI cognition without financial credentials
  • Research-side RL with governed promotion

Three-Tier Structure

  • Tier-1: Financial authority, policy/admission, execution gateway, and ledger management
  • Tier-2: AI cognition, tool use, research coordination, memory management
  • Shared Code: Deterministic engine with separate instances for live and simulation

Architecture Issues Summary

Single Kernel Point of Failure

critical
Resilience

The production Tier1 kernel is the sole execution owner with no visible hot standby or failover mechanism.

Single Broker Vendor Lock-in

high
Extensibility

OpenAlgo is the sole broker boundary with no adapter abstraction visible.

SQLite Scalability Ceiling

high
Scalability

SQLite WAL has fundamental limitations for high-throughput financial workloads.

Cognition-Decision Feedback Oscillation

medium
Stability

The bidirectional flow creates potential for oscillation.

Missing Idempotency Guarantees

high
Transaction Safety

The architecture does not explicitly show idempotency keys at transaction boundaries.

Ambiguous Result Taxonomy Incomplete

high
Transaction Safety

The result taxonomy needs formal specification.

Review Recommendations

Immediate Actions

  • Implement Broker Adapter Abstraction: Create a formal BrokerAdapter port to enable multi-broker support and eliminate single-vendor dependency
  • Add Idempotency Layer: Implement idempotency keys at every external boundary to prevent duplicate execution

Short-Term Improvements

  • Kernel High Availability: Implement active-passive kernel replication with automatic failover
  • Formal Simulation Isolation: Implement capability-based security to guarantee simulation cannot access live broker credentials
  • Comprehensive Observability Stack: Implement structured logging, OpenTelemetry tracing, and alerting rules

Medium-Term Enhancements

  • Database Migration Path: Plan migration from SQLite to PostgreSQL or distributed database
  • Cognitive Layer Stability: Add cooldown periods and proposal deduplication to prevent oscillation
  • Multi-Signature Governance: Evolve owner governance to support multi-signature approval
